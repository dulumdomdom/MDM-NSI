# Масштабирование: от демо-стенда к рабочей системе

Сейчас «сервер» живёт в браузере (MSW): удобно для показа и обучения, но данные у каждого ПК свои.
Ниже — путь к многопользовательской системе в закрытом контуре и что делать при росте объёмов.

## 1. Этапы

| Этап | Что сделать | Результат |
|---|---|---|
| **0. Демо** (сейчас) | офлайн-пакет, `VITE_USE_MOCKS=true` | показ, обучение, согласование настроек |
| **1. Пилот** | бэкенд по `docs/API.md`, одна БД, `VITE_USE_MOCKS=false`, nginx/IIS (`deploy/`) | общие данные для одного-двух отделов |
| **2. Промышленная эксплуатация** | LDAP/AD, HTTPS, резервирование, интеграции через брокер, мониторинг | вся номенклатура завода, 1С / АСУ / Imbase |
| **3. Рост** | серверный поиск и пагинация, реплики чтения, очереди | сотни тысяч позиций, сотни пользователей |

## 2. Бэкенд

- **Технология — любая**, важен контракт `docs/API.md`. Если бэкенд на Node.js/TypeScript —
  `src/lib` (движок классификатора, RBAC, маршрут, умный поиск, интеграции) переносится **как есть**:
  это чистые функции без Vue и браузера. На другом стеке — портировать, сверяясь с тестами `src/lib/**/__tests__`.
- **Эталон поведения** — `src/mocks`: каждая проверка прав, валидация, побочный эффект.
  Тесты `src/mocks/__tests__` — готовый список сценариев для серверных тестов.
- **БД — PostgreSQL** (рекомендуется):
  - справочники с произвольными атрибутами — `elements(id, catalog_id, parent_id, state, attributes jsonb, …)`
    + GIN-индекс по `attributes`, частичные индексы по часто ищущимся атрибутам;
  - конфигурации справочников, классификаторов, обходных листов — `jsonb` с версией (оптимистичная блокировка);
  - история изменений, журнал действий, журнал обмена — отдельные таблицы с партиционированием по месяцу;
  - уникальность шифра — уникальный индекс `(classifier_id, catalog_id, normalized_code)`.
- **Аутентификация:** LDAP/AD предприятия (уже есть в модели пользователя), токены с коротким сроком
  жизни + обновление; локальные учётные записи — SHA-512 с солью или лучше Argon2/bcrypt на сервере.

## 3. Горизонтальное масштабирование

- Бэкенд **без состояния** (сессия — в токене) → несколько экземпляров за nginx (`deploy/nginx.conf`, `upstream`).
- **Фоновые задачи** — отдельный процесс-воркер: расписание потоков обмена, импорт, уведомления,
  напоминания о просроченных строках. Не запускать расписание в каждом экземпляре API — один планировщик
  или блокировка в БД (`pg_try_advisory_lock`).
- **Чтение** — реплика PostgreSQL для поиска, отчётов и выгрузок; запись — в основной узел.
- **Статика** (`dist/`) — на nginx с долгим кешем `/assets/*` (имена с хэшем), `index.html` — без кеша.

## 4. Большие объёмы данных

Сейчас клиент загружает справочник целиком и ищет в браузере: комфортно до ~10–20 тыс. позиций
(таблица уже виртуализирована, поиск ~50 мс на 1 500 позиций). Дальше:

1. **Серверная пагинация и поиск:** добавить в `GET /catalogs/{id}/elements` параметры
   `q, mode, parentId, offset, limit, sort` → в `stores/catalog.ts` заменить локальный `search()` на запрос.
   Нормализацию из `lib/smartSearch.ts` применить на сервере при индексации (колонка `search_tokens`).
2. **Полнотекстовый поиск:** PostgreSQL `tsvector` + `pg_trgm` для опечаток; при сотнях тысяч позиций
   и сложной морфологии — OpenSearch/Elasticsearch (ставится в контуре из офлайн-дистрибутива).
3. **Справочники-ссылки** (`ReferencePicker`) — поиск по серверу вместо полного списка.
4. **Выгрузка CSV** больших справочников — на сервере, потоково.

## 5. Интеграции

- **Транспорт:** RabbitMQ (уже указан для АСУ) или Kafka — для событий «элемент изменён»;
  1С — HTTP-сервисы / шина 1С; Imbase — чтение из её БД или выгрузки XML.
- **Надёжность:** outbox-таблица в той же транзакции, что и изменение элемента → воркер отправляет,
  повторяет с паузами, складывает в журнал обмена; идемпотентность по `externalId`.
- **Сопоставления полей и расписания** — уже данные (`IntegrationFlow`); новая система = новая запись,
  не код (кроме адаптера протокола).

## 6. Безопасность и эксплуатация

- HTTPS с сертификатом внутреннего УЦ; заголовки `Content-Security-Policy`, `X-Frame-Options`.
- RBAC — **на сервере**: колонки и строки фильтровать в запросе к БД, не на клиенте.
- Журнал действий — неизменяемый (только вставка), срок хранения по регламенту ИБ.
- Резервное копирование БД (полное + WAL), проверка восстановления.
- Мониторинг: метрики API (время ответа, ошибки), длина очереди обмена, число просроченных строк заявок.
- Обновления: сборка в CI контура (`.gitlab-ci.yml`), выкладка `dist/` атомарной заменой каталога.

## 7. Производительность фронтенда

- Маршруты загружаются лениво; тяжёлые вендоры — отдельные чанки (`vite.config.ts`).
- Самый тяжёлый экран — справочник (~320 КБ модуль): при росте числа типов полей разнести поля формы
  по динамическим импортам.
- Таблица виртуализирована; при серверной пагинации — бесконечная прокрутка вместо полного списка.
